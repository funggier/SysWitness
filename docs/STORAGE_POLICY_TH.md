# SysWitness — นโยบายพื้นที่เก็บข้อมูลและ Retention

> เริ่มมีความสามารถในรุ่น Prototype M2 นี้ **ไม่มี API ที่อนุญาตให้โปรแกรมภายนอกสั่งลบหรือเปลี่ยนการตั้งค่าการเก็บข้อมูล**

## จุดมุ่งหมาย
SysWitness มีหน้าที่เก็บหลักฐานกิจกรรม ไม่ใช่เครื่องมือจัดการความปลอดภัยหรือควบคุมระบบ จึงออกแบบการจัดเก็บอย่างระมัดระวัง โดยไม่ลบข้อมูลโดยไม่แจ้งไว้ในประวัติ และไม่เพิ่มตำแหน่ง Bookmark หากการบันทึก Event ยังไม่สำเร็จ

## ค่าเริ่มต้นและการตั้งค่าภายใน

| ตัวแปร Environment | ค่าเริ่มต้น | ผลการทำงาน |
|---|---:|---|
| `SYSWITNESS_STORAGE_SOFT_LIMIT_MB` | `4096` (4 GiB) | ขีดจำกัดโดยประมาณของไฟล์ SQLite + WAL + SHM; เลือกค่า 16–1,048,576 MiB |
| `SYSWITNESS_RETENTION_DAYS` | **ไม่กำหนด = ปิด** | ถ้าต้องการให้ลบหลักฐานเก่าตามนโยบาย ให้กำหนด 1–3650 วันอย่างชัดเจน |
| `SYSWITNESS_DATA_DIRECTORY` | `data/` ข้างโปรแกรม | เปลี่ยนโฟลเดอร์เก็บฐานข้อมูลโดยตั้งค่าจากเครื่องเอง ไม่ผ่าน API |

ตัวอย่างเปิด Retention เป็น 30 วันจาก PowerShell ก่อนรันโปรแกรม:

```powershell
$env:SYSWITNESS_RETENTION_DAYS = '30'
$env:SYSWITNESS_STORAGE_SOFT_LIMIT_MB = '8192'
dotnet run --project src/SysWitness.Api
```

หากไม่ต้องการลบหลักฐานเก่า **อย่าตั้งค่า `SYSWITNESS_RETENTION_DAYS`** ค่าปกติจะเก็บข้อมูลต่อไปเรื่อย ๆ จนกว่าจะถึง Soft Limit หรือผู้ใช้จัดการข้อมูลนอกโปรแกรมเอง

## ระบบ Retention

- ใช้ **เวลาที่ SysWitness สังเกตเหตุการณ์ (`observed_at_utc`)** ไม่ใช่เวลาที่ Windows ระบุว่าเหตุการณ์เกิด เพื่อไม่ลบหลักฐานเก่าที่เพิ่งนำเข้ามาใหม่ทันที
- เมื่อเปิดใช้งาน จะตรวจหลักฐานที่หมดอายุเป็นรอบ ๆ ประมาณทุก 1 นาที
- ประมวลผลแบบแบ่ง Batch จำกัดจำนวน เพื่อไม่ให้ล็อกฐานข้อมูลนานเกินไป
- การลบ Event และการบันทึก **สรุปการลบราย Channel** จะอยู่ใน SQLite Transaction เดียวกัน
- ประวัติการลบระบุเวลา จำนวนเหตุการณ์ที่ลบ ช่วงเวลาเก็บข้อมูล และ Cutoff แต่ **ไม่เก็บ Payload หรือรายละเอียดส่วนตัวที่ถูกลบ**
- **ไม่แตะ Windows Event Log ต้นทาง** และ **ไม่เปลี่ยน Event Bookmark**
- ประวัติ Retention ไม่ใช่สำเนาหลักฐานที่กู้คืน Event เดิมได้

## Soft Limit: เมื่อพื้นที่ใกล้เต็ม

- ประเมินขนาดไฟล์ `events.sqlite`, `events.sqlite-wal`, `events.sqlite-shm` และขนาด Batch ที่กำลังจะเก็บ
- หากประเมินว่าเพิ่มอีก Batch แล้วเกิน Soft Limit จะหยุด **การบันทึก Batch นั้น** โดยไม่ปรับ Bookmark
- Collector จะรายงานสถานะ `degraded` พร้อม `storage_soft_limit_reached` เพื่อบ่งบอกว่าเก็บข้อมูลเพิ่มไม่ได้
- ไม่ลบหลักฐานเก่าอัตโนมัติเพื่อให้เขียนต่อ (การลบจะเกิดเฉพาะกรณีผู้ใช้ตั้ง Retention)
- เมื่อมีพื้นที่เพียงพอหรือปรับเกณฑ์ด้วยการตั้งค่า Local แล้ว Collector จะสามารถพยายามอ่านต่อได้ หาก Event ต้นทางยังอยู่
- หาก Windows Event Log ต้นทางถูกเขียนทับระหว่างหยุดรับข้อมูล เหตุการณ์นั้นอาจสูญหาย; ระบบพยายามบันทึก Coverage Gap ตามหลักฐานที่ตรวจได้

**Soft Limit ไม่ใช่ Hard Disk Quota** เนื่องจาก SQLite/WAL และไฟล์ระบบอาจใช้พื้นที่เพิ่มในระหว่าง Transaction/Index และการลบ Row ไม่ได้ทำให้ไฟล์ SQLite มีขนาดเล็กลงทันที ไม่มี Auto-VACUUM ในรุ่นนี้ จึงไม่ควรอ้างว่าตั้ง 4 GiB แล้วไฟล์จะไม่มีวันเกิน 4 GiB

การเปิด Retention ช่วยให้ SQLite นำพื้นที่ภายในที่ถูกลบกลับมาใช้ได้ แต่จะไม่บังคับลดขนาดไฟล์ฐานข้อมูลกลับลงมาให้ต่ำกว่า Soft Limit โดยอัตโนมัติในรุ่นนี้ ต้องตรวจพื้นที่จริงและพิจารณาเครื่องมือซ่อมบำรุงแยกในอนาคต

## API สำหรับตรวจดู (Read-only)

```http
GET /api/v1/storage/status
GET /api/v1/storage/retention?limit=50
```

ทั้งสอง Endpoint ต้องยืนยันตัวตนด้วย Token เช่นเดียวกับ API ข้อมูลอื่น โดยตอบแค่สถิติรวมและประวัติการลบ ไม่มีคำสั่งแก้ Retention หรือสั่งลบ Event ผ่าน API

## การตรวจสอบ
มีชุดทดสอบที่ยืนยันการปิด Retention โดยค่าเริ่มต้น การลบแบบ Opt-in การไม่เลื่อน Bookmark การบันทึกสรุปการลบแบบ Durable และการหยุดบันทึกเมื่อ Soft Limit ไม่เพียงพอ พร้อมทดสอบ API บน Windows จริง

## งานที่ยังไม่รองรับ
- Hard quota ที่รับประกันขนาดไฟล์ไม่เกิน
- ระบบ Reclaim/Disk Compaction อย่างปลอดภัยตามเงื่อนไขพื้นที่ว่าง
- Disk-free-space Guard, ตรวจจับ IO/NTFS Error เชิงลึก
- การตั้งค่าผ่าน GUI/ไฟล์ Local แบบมีการตรวจสิทธิ์ (ขณะนี้ใช้ Environment)
- การพิสูจน์ความถูกต้องแบบ End-to-End และสำรองข้อมูลหลักฐานแบบ Immutable
